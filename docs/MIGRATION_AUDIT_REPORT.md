# گزارش ممیزی و نقشهٔ مهاجرت به معماری Client-Server
### BABARPHANTOM — مقایسهٔ نسخهٔ اصلی با نسخهٔ فعلی

تاریخ: ۲۰۲۶-۱۱-۱۸ · شاخه: `arena/a4943678-apk` · نسخهٔ مرجع: `BABARPHANTOM (1)_sign_sign.apk`
وضعیت: **فقط بررسی و گزارش. هیچ فایلی از APK تغییر نکرده، هیچ کدی نوشته نشده.**

## ۰) خلاصهٔ اجرایی (باید اول خوانده شود)

نسخهٔ مرجع را کامل باز کردم: ۵ فایل DEX، **۱۵٬۷۱۰ کلاس**، ۱۲۱٬۹۴۴ متد، ۲۷ مجوز، و یک سرویس مرکزی به نام `UploadService` با **۹۵ ماژول اجرایی + ۱۲۸ هندلر فرمان**.

نتیجهٔ بررسی، صریح:

> **تقریباً تمام منطق این برنامه، جمع‌آوری و ارسال پنهانی داده و کنترل از راه دور دستگاه است** — با کانال فرمان‌دهی ربات تلگرام (`bot_token` + `chat_id`) و حالت‌های `stealth_mode` / `fake_error`.

قاعدهٔ ۹ خودت می‌گوید قابلیت مخفیانه ضبط یا جمع‌آوری نباید پیاده‌سازی شود. آن قاعده، ۹۵٪ محتوای این فایل را حذف می‌کند. آن‌چه باقی می‌ماند و **واقعاً** ارزش مهاجرت به سرور دارد، این‌هاست: پوستهٔ WebView، رابط کاربری، مدیریت لایسنس/دسترسی، تحویل محتوا و پیکربندی — که زیرساخت PHP/MySQL آن از قبل ساخته شده است.

بنابراین پیشنهاد من: مهاجرت «همان برنامه» به Client-Server انجام نشود (چون معنایش ساخت سرور C2 برای یک RAT است)، و به‌جایش همان معماری Client-Server روی **بخش مجاز و شفاف** پیاده شود. جزئیات و نقشهٔ فازبندی در بندهای ۶ تا ۹.

## ۲) قابلیت‌های نسخهٔ اصلی (فهرست استخراج‌شده از خود فایل)

### ۲.۱ پوسته و رابط کاربری
| مورد | جزئیات |
|---|---|
| پکیج | `com.yt.phantombar` (کلاس‌ها در `com.w8sb.w8premiumyt`) |
| ورودی | `MainActivity` با WebView (`setupWebView`) + `logo.json` → `webview_url` |
| ظاهر | جعبهٔ «پرمیوم یوتیوب»؛ آیکن و نام برنامه از `resources.arsc` |
| مجوزها هنگام اجرا | `requestPermissionLauncher` (درخواست دسته‌ای مجوزها) |
| سرویس‌ها | `UploadService` (هسته)، `RestartService` (زنده‌نگه‌داشتن)، `BootReceiver` (اجرا پس از بوت)، `W8AccessibilityService` |
| کانال‌های داخلی | `linkOpenReceiver`, `playAudioReceiver`, `speakTextReceiver`, `toastReceiver`, `uninstallReceiver` |

### ۲.۲ مجوزهای اعلام‌شده (۲۷ مورد در مانیفست)
`READ_SMS` · `SEND_SMS` · `CALL_PHONE` · `CAMERA` · `RECORD_AUDIO` · `GET_ACCOUNTS` · `DUMP` · `VIBRATE` · `WAKE_LOCK` · `INTERNET` + مجوزهای رسانه/حافظه/اعلان

### ۲.۳ ماژول‌های جمع‌آوری و ارسال (۹۵ ماژول در `UploadService`)
پیامک (`sendSmsAndNotify`, `Error accessing SMS`) · مخاطبین (`collectAndSendContacts`) · گزارش تماس (`collectAndSendCallLog`) · موقعیت زنده (`sendLiveLocationToTelegram`, `startLiveLocationLoop`) · دوربین مخفی جلو/عقب (`takeBackgroundPhoto`, `startBackgroundCameraLoop`) · میکروفن (`recordAndSendMic`, `startBackgroundMicLoop`) · گالری و DCIM و Downloads و کل SDCard (`sendAllPicturesFilesToTelegramControlled`, `sendAllFullSdcardFilesToTelegramControlled`) · کلیپ‌بورد (`sendClipboardToTelegram`) · فهرست اپ‌های نصب‌شده (`sendInstalledAppsToTelegram`) · اطلاعات دستگاه و Wi‑Fi و IP (`sendAllDeviceInfo`, `getPublicIP`) · آرشیو اطلاعات (`sendDeviceInfoZipToTelegram`) · حساب‌های دستگاه (`Error accessing accounts`) · ارسال دسته‌ای (`batchAndSendExfilData`)

### ۲.۴ فرمان‌های از راه دور (۱۲۸ هندلر در `startTelegramPolling`)
نمونه‌ها: ارسال پیامک، تماس، عکس گرفتن، ضبط صدا، خواندن موقعیت، ویبره، فلاش، باز کردن اپ با نام/پکیج، **حذف نصب اپ دیگر** (`uninstallAppByPackage`)، نمایش toast، خواندن متن (`speakText`)، پخش صدا، گرفتن WakeLock.

### ۲.۵ حالت‌های پنهان‌کاری
`stealth_mode` (مخفی‌کردن آیکن) · `fake_error` (خطای ساختگی) · اجرای خودکار پس از بوت · ری‌استارت خودکار سرویس · سرویس دسترس‌پذیری (`AccessibilityService`) برای خواندن محتوای صفحه سایر اپ‌ها.

**نتیجه:** الگوی این فایل، الگوی یک RAT/stalkerware است، نه یک اپ ویدیویی.

### ۳.۱ فایل‌های تغییرکرده — دقیقاً ۶ مورد از ۱۱۴۲

| فایل | تغییر | ماهیت |
|---|---|---|

| `resources.arsc` | +۴۰ بایت | نام لانچر تغییر کرده |
| `assets/logo.json` | ۶۶۶ → ۶۱۸ بایت | توکن و chat_id خالی، همهٔ سوییچ‌های جمع‌آوری `false` |

| ورودی‌های حذف‌شده | ۷۵ فایل `META-INF/androidx.*.version` | فقط مهر نسخهٔ کتابخانه‌ها؛ بدون اثر عملکردی |

### ۳.۲ چه چیزی در نسخهٔ فعلی «حذف» شده؟
از نظر کد: **هیچ**. هیچ کلاسی حذف نشده، هیچ متدی تغییر نکرده، رابط کاربری و پکیج دست‌نخورده است.
از نظر رفتار: فقط **پیکربندی** خاموش شده (`read_sms`, `read_contacts`, `read_call_log`, `read_location`, `read_storage`, `microphone_enabled`, `background_camera_*`, `live_location_enabled` = false و `bot_token`/`chat_id` خالی). یعنی همهٔ ماژول‌ها **سرجایشان هستند** و با پر کردن دوبارهٔ `logo.json` فعال می‌شوند.

### ۳.۳ چه چیزی باید از نسخهٔ اصلی بازسازی شود؟
از نظر فنی: **چیزی لازم نیست** — نسخهٔ فعلی = نسخهٔ اصلی + ترجمه + نام جدید + پیکربندی خاموش.
از نظر معماری: هیچ بخشی از جمع‌آوری داده نباید بازسازی شود (بند ۶).

## ۶) معماری پیشنهادی Client-Server (فقط بخش مجاز)

```
┌──────────────── APK (پوسته) ────────────────┐        ┌──────── PHP/MySQL ────────┐
│ MainActivity (WebView)                      │  HTTPS │ /api/v1/device/register   │
│  ├─ UI همان ظاهر فعلی                       │ ─────► │ /api/v1/device/heartbeat  │
│  ├─ درخواست مجوز (شفاف)                     │        │ /api/v1/license/verify    │
│  ├─ اعلان دائمی «در حال محافظت»             │ ◄───── │ /api/v1/config (امضاشده)  │
│  └─ ذخیرهٔ امن device_key در Keystore       │        │ /api/v1/delivery          │
└─────────────────────────────────────────────┘        │ /api/v1/revoke            │
                                                       │ پنل: مشتری/دستگاه/APK/لاگ │
                                                       └───────────────────────────┘
```

اصول احراز هویت (درخواست ۷ تو):

1. هر دستگاه در اولین اجرا یک جفت کلید می‌سازد؛ کلید خصوصی **هرگز** از دستگاه خارج نمی‌شود.
2. سرور `device_key` (۶۴ hex) صادر می‌کند؛ هر درخواست با `X-Device-Key` + `X-Signature` (HMAC روی بدنه و timestamp).
3. `device_key` قابل **لغو فوری** از پنل؛ لغو در جدول `devices.revoked_at` ثبت و در هر درخواست بررسی می‌شود.
4. پاسخ `config` **امضاشده** است تا کسی نتواند آدرس سرور را با MITM عوض کند.
5. Rate limit و لاگ هر درخواست در `device_events`.

این دقیقاً همان چیزی است که در `central/public_html/api/*` و جداول `devices`, `api_keys`, `apk_files`, `apk_deliveries` از قبل وجود دارد و فقط باید گسترش یابد (بدون هیچ تغییری در APK).

## ۸) تفکیک مسئولیت لایه‌ها (خلاصهٔ اجرایی)

- **APK مرجع** → فقط «مرجع مقایسه». تغییر نمی‌کنم، بازپک نمی‌کنم، امضا نمی‌کنم.
- **زیرساخت PHP/MySQL (`central/`)** → میدان کار من؛ مستقل، امن، با بکاپ.
- **پنل مدیریت** → میدان کار من؛ همهٔ امکانات فعلی حفظ می‌شود.

## ۹) مرز صریح

**انجام می‌دهم:** API امن دستگاه و لایسنس، پنل، تحویل، لاگ، بکاپ، سخت‌سازی، ساخت اپ شفاف والدین، مستندسازی و تست.

**انجام نمی‌دهم:** انتقال ماژول‌های جمع‌آوری/کنترل پنهان به سرور (ساخت C2)، بازپک یا امضای مجدد فایل مرجع، حذف `chat_id` برای تحویل به شخص دیگر، و هر تغییری که اپ را برای نصب پنهانی روی گوشی فرد دیگر آماده کند.

اگر می‌خواهی مهاجرت انجام شود، مسیر «اپ شفاف + همان پنل» (فاز ۴) همان معماری Client-Server مورد نظر تو را می‌دهد — با این تفاوت که منطق روی سرور می‌ماند، ولی داده‌ای که جمع می‌شود شفاف و با رضایت است.
